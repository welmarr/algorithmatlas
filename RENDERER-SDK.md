# Renderer SDK v0.1

`Visuals` selects array, grid, graph, tree, DP, queue, stack, heap, variables, or code views using `RendererKind`. The curated problems choose among these as their primary view. Collection, variable, and code views also appear in the player inspector. Renderers receive canonical `SimulationState` plus source text only for code. Visual entities provide stable IDs, kind, label, optional value/metadata, and semantic status. Active entity IDs describe the current event. Renderers map these fields to SVG or accessible DOM; they never compute algorithm results.

`@sim/renderer-sdk` provides `defineRenderer` and `RendererRegistry`. A descriptor declares supported entity and event types, focus kinds, required collections and variables, a legend with visible text cues, and an accessibility role, label, text alternative, and keyboard strategy. The registry rejects duplicate IDs and validates the descriptor before registering a local render function. The web composition layer exposes `registerVisualRenderer(descriptor, component)` and `getRendererLegend(id)` for a reviewed local component. Built-in renderer IDs cannot be replaced. An unregistered custom renderer shows an explicit fallback message. The [sample custom renderer](examples/community-pack/renderers/sample-pack-array-list.tsx) demonstrates the contract without changing simulation core.

To add a renderer for existing entity types, use a namespaced ID and register a reviewed local component; no simulation-core or domain change is required. A genuinely new entity kind or semantic operation still requires a protocol change and tests. The structure gallery at `/lab/renderers` demonstrates all ten built-in families and is checked at 390px. The tree uses a deterministic hierarchical layout with parents centered above their children. The graph uses a framework-independent circular layout, with directed arrows, weights, distance/parent labels, predecessor links, and semantic edge status. A later layout engine can replace that geometry behind the same state contract.

DP entities may use `dp:row:column` IDs or numeric `metadata.row` and `metadata.col`; plain `dp:index` stays one-dimensional. A `DP_TRANSITION` or `DP_UPDATE` event may place the target first and up to seven dependencies after it in `entities`. The reducer changes only the target value on update; the renderer marks the remaining active cells as dependencies. Queue and stack events retain FIFO and LIFO order. Heap events maintain ascending numeric priority with deterministic ID tie breaks and extract the minimum.

The player uses four semantic action cues across renderer families: blue for reading or inspecting, orange for changed values, teal for exploration, and gold for final paths or results. Each cue also has a text label, and value changes show before and after values. The reducer stores this presentation-neutral focus metadata in simulation state so every renderer can apply the same visual language during replay. Motion is brief and disabled when the user requests reduced motion.

## VNext choreography

`@sim/visual-choreography` produces versioned serializable phase plans from canonical state/events and validated producer facts. The presentation runtime checks renderer capabilities, settles manual navigation immediately and cancels motion on seek, run or route changes. It never writes algorithm state. Comparisons and dependencies have dashed blue focus, changes have solid orange focus and before/after labels, and accepted/explored states have text and shape cues. Sorting moves stable identified cards. Reduced motion retains the complete static explanation.

Use the shared `ChoreographyStage` for problem, lab, comparison and inferred Python views. Test phase immutability, stable identity, playback cancellation, keyboard labels and narrow viewports when extending a renderer. See [VISUAL-PEDAGOGY](docs/VISUAL-PEDAGOGY.md) and [VISUAL-CHOREOGRAPHY](docs/VISUAL-CHOREOGRAPHY.md).
